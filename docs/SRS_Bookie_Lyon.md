# Bookie Lyon — ระบบจองโต๊ะผ่าน LINE

**เวอร์ชัน:** 1.0 (ฉบับร่างเพื่อทบทวน)  
**วันที่:** 9 พฤศจิกายน 2569  
**สถานะ:** ข้อกำหนดเสนอ ยังไม่ผ่านการอนุมัติจากผู้มีส่วนได้ส่วนเสีย  
**แหล่งข้อมูล:** `Bookie-Lyon-Pitch-Deck (1).html`, `Bookie-Lyon-Explainer.html`, `TECH_STACK_PLAN.md`, `backend/BACKEND_PLAN.md`, `backend/BACKEND_FEATURE_STACK.md` และ `backend/เอกสาร Backend.pdf`

## 1. บทนำ

### 1.1 วัตถุประสงค์

เอกสารนี้กำหนดความต้องการของ Bookie Lyon เพื่อให้ทีมผลิตภัณฑ์ นักพัฒนา ผู้ทดสอบ และผู้เกี่ยวข้องใช้เป็นฐานร่วมกันในการออกแบบ พัฒนา และตรวจรับระบบจองโต๊ะร้านผ่าน LINE OA โดยระบุเรื่องที่ยังต้องตัดสินใจแยกจากขอบเขตที่เสนอ

### 1.2 ปัญหาและเป้าหมาย

ร้านรับจองผ่านแชทหรือโทรศัพท์ พนักงานต้องตอบ ตรวจโต๊ะ และบันทึกด้วยตนเอง อาจตอบช้าและจองซ้อน ระบบเสนอให้ลูกค้าจองผ่าน LINE ของร้าน เห็นสถานะโต๊ะ ส่งคำขอเข้าคิวเดียวกับการจองแทนโดยพนักงาน และให้ร้านจัดการรายการในที่เดียว ผลประหยัดเวลาหรือความเร็วจริงยังต้องวัดในการทดลอง

### 1.3 ขอบเขต

**MVP ที่เสนอเพื่อยืนยัน:** เชื่อม LINE และเปิดหน้าจอง, ตั้งค่าร้าน/โซน/โต๊ะ/กฎ, ลูกค้าจองเอง, พนักงานจองแทน, จัดคิวและป้องกันการจองซ้อน, ดูผลและรายการจอง, ส่งการแจ้งเตือนเมื่อเชื่อม LINE ได้

**ขอบเขตเพิ่มเติมรอตัดสินใจ:** มัดจำ ชำระเงิน ยกเลิกและคืนเงิน ออกแบบในเอกสาร backend แต่ pitch deck ระบุว่ายังไม่มีมัดจำและยังไม่ครอบคลุมการยกเลิก จึงไม่ถือเป็น MVP ที่อนุมัติแล้ว ดู §8 และ §11

**นอกขอบเขต MVP ที่เสนอ:** POS, ระบบรายงานเชิงวิเคราะห์, ระบบจัดเก็บค่าสมาชิกร้าน, marketplace ค้นหาร้าน และการรับประกันผลทางธุรกิจ ระบบ check-in และปล่อยโต๊ะอัตโนมัติเมื่อไม่มา รอการตัดสินใจ

### 1.4 คำศัพท์

| คำ | ความหมาย |
| --- | --- |
| LINE OA | บัญชี LINE Official Account ของร้าน |
| LIFF | เว็บแอปที่เปิดผ่าน LINE |
| ร้าน (venue) | หน่วยข้อมูลและขอบเขตสิทธิ์ของร้านแต่ละแห่ง |
| คืนบริการ (service night) | ช่วงบริการที่ผูกกับวันที่เริ่มต้น แม้สิ้นสุดหลังเที่ยงคืน |
| Draft | ตัวเลือกที่ยังไม่ส่งคำขอ ไม่มีการกันโต๊ะหรือสิทธิ์ในคิว |
| FIFO | พิจารณาตามลำดับที่ระบบคิวรับคำขอ ภายในร้านและคืนบริการเดียวกัน |
| Hold | การกันโต๊ะชั่วคราวระหว่างรอชำระเงิน หากเปิดใช้มัดจำ |
| Known customer | ลูกค้าที่มีความสัมพันธ์กับร้านและมี identity ที่ระบบระบุได้ |
| Policy snapshot | สำเนานโยบายที่ผูกกับรายการจอง ณ เวลาสร้างรายการ |

## 2. ภาพรวมระบบ

### 2.1 ผู้ใช้งานและสิทธิ์

| ผู้ใช้งาน | หน้าที่ |
| --- | --- |
| ลูกค้า | เปิดหน้าจอง ดูโต๊ะ ส่งคำขอ ติดตามผลและดูรายการของตน |
| เจ้าของร้าน | ตั้งค่าร้าน LINE โซน โต๊ะ กฎ และจัดการรายการตามสิทธิ์ |
| พนักงาน | ค้นลูกค้าที่ร้านรู้จัก จองแทน และดูหรือจัดการรายการตามสิทธิ์ที่ได้รับ |
| ผู้ดูแลระบบ | ดูแลโครงสร้างและแก้ปัญหาระบบ ขอบเขตเครื่องมือดูแลรอยืนยัน |
| ระบบภายนอก | LINE และผู้ให้บริการชำระเงินเมื่อเปิดใช้ |

เจ้าของและพนักงานต้องเป็นสมาชิกของร้านที่เกี่ยวข้อง การเข้าสู่ระบบเพียงอย่างเดียวไม่ให้สิทธิ์เข้าถึงทุกร้าน

### 2.2 สภาพแวดล้อมและข้อพึ่งพา

ลูกค้าใช้ LIFF บนอุปกรณ์มือถือที่รองรับ LINE; เจ้าของและพนักงานใช้เว็บหลังบ้าน ต้องมีอินเทอร์เน็ต ระบบพึ่งพา LINE สำหรับตัวตนและการส่งข้อความ และบริการฐานข้อมูล/คิวตามสถาปัตยกรรมที่เลือกจริง การส่งข้อความจาก OA ต้องตั้งค่า provider และ channel ที่สัมพันธ์กัน การมีลิงก์เพียงอย่างเดียวไม่ยืนยันว่าระบบส่งข้อความได้

### 2.3 สมมติฐานและข้อจำกัด

- หนึ่งโต๊ะมีการจัดสรรที่ active ได้หนึ่งรายการต่อคืนบริการ เป็นข้อเสนอชั่วคราว ต้องยืนยันว่ารองรับหลายรอบหรือไม่
- สถานะโต๊ะที่แสดงเป็น snapshot อาจเปลี่ยนระหว่างผู้ใช้ตัดสินใจ ผลสุดท้ายตัดสินฝั่ง server
- การส่งคำขอได้รับการรับเข้าคิว ไม่เท่ากับจองสำเร็จ ลำดับวัดจากเวลาที่ broker รับ ไม่ใช่เวลาเปิดหน้าเว็บหรือเวลาบนอุปกรณ์
- ยังไม่มีระบบ backend, endpoint จริง, ผล pilot หรือ load test ที่ยืนยันในแหล่งข้อมูล
- เอกสาร `FEATURE_REQUIREMENTS.md`, `OPEN_DECISIONS.md`, `COST_PLAN.md` และ `LINE_ONBOARDING_GUIDE.md` ถูกอ้างในแผน แต่ไม่พบใน workspace จึงยังยืนยันรายละเอียดจากเอกสารเหล่านั้นไม่ได้

## 3. ความต้องการเชิงหน้าที่

รหัส FR ใช้ติดตามข้อกำหนด การทดสอบต้องครอบคลุมเงื่อนไขสำเร็จและผิดพลาด สิทธิ์จัดการรายการละเอียดรออนุมัติใน §11

| FR-01 | เจ้าของตั้งค่าการเชื่อม LINE แยกร้าน | ร้านแต่ละแห่งมี configuration ของตน และผู้ไม่มีสิทธิ์แก้ไม่ได้ |

## 4. กฎธุรกิจและสถานะ

1. สิทธิ์รับโต๊ะเกิดจากการประมวลผลสำเร็จ ไม่เกิดจากการเปิดหน้าหรือบันทึก draft
2. ทั้งลูกค้าและพนักงานใช้ FIFO เดียวกันตามร้านและคืนบริการ ไม่ใช้ลำดับเวลาบนเครื่องลูกค้า
3. ระบบต้องบังคับความถูกต้องที่ฐานข้อมูลเมื่อมีคำขอพร้อมกัน ภายใต้ข้อเสนอหนึ่งโต๊ะต่อคืน
4. ราคาโต๊ะกับมัดจำเป็นข้อมูลคนละประเภท ราคาไม่กำหนดไม่ได้แปลว่าไม่มีมัดจำเสมอ หากมีการเปิดใช้มัดจำ
5. การส่งข้อความล้มเหลวไม่ย้อนการจองที่บันทึกสำเร็จ
6. วันคืนบริการและเวลาเปิดรับต้องคำนวณจาก timezone ของร้าน ข้อกำหนดค่าเริ่มต้นรอยืนยัน

**สถานะคำขอที่เสนอ:** `pending_publish`, `queued`, `processing`, `held`, `confirmed`, `rejected` โดย `held` ใช้เมื่อเปิดมัดจำเท่านั้น; รายละเอียดการแสดงสถานะให้ผู้ใช้รอยืนยัน  
**สถานะการจองที่เสนอ:** `confirmed` เป็นแกน MVP; `pending_payment`, `expired`, `cancelled`, `checked_in`, `completed`, `no_show` ขึ้นกับฟีเจอร์และกฎที่อนุมัติ

## 5. ความต้องการส่วนติดต่อ

### 5.1 ส่วนติดต่อผู้ใช้

- **ลูกค้า:** หน้าร้านและกฎ, เลือกคืน/เวลา/จำนวนคน/โซน/โต๊ะ, สรุปก่อนยืนยัน, สถานะคำขอ, รายการและรายละเอียดยืนยัน ต้องแสดงข้อความเมื่อโต๊ะไม่ว่างหรือเกิดข้อผิดพลาด
- **เจ้าของ/พนักงาน:** เข้าสู่ระบบ, รายการจอง, ค้นลูกค้าและจองแทน; เจ้าของมีหน้าตั้งค่าร้าน โต๊ะ กฎ และ LINE ตามสิทธิ์
- รองรับจอมือถือใน flow ลูกค้า แสดงสถานะกำลังประมวลผลอย่างชัดเจน ไม่แสดงว่าได้โต๊ะก่อนผลยืนยัน

### 5.2 ส่วนติดต่อระบบภายนอก

- **LINE Login/LIFF:** ตรวจ token และ provider ที่เกี่ยวข้องฝั่ง server
- **LINE Messaging API:** ส่งข้อความจาก OA ร้านเมื่อเปิดใช้งานและตั้งค่าถูกต้อง; ตรวจ signature และ channel/destination ของ webhook พร้อมป้องกัน event ซ้ำ
- **ระบบคิว:** รับคำขอแบบ FIFO แยกกลุ่มตามร้านและคืนบริการ พร้อมกลไกกู้คืนกรณีส่งหรือประมวลผลล้มเหลว
- **Payment provider:** เฉพาะเมื่ออนุมัติขอบเขต §8; provider และเส้นทางเงินจริงยังไม่เลือก

### 5.3 API ที่เสนอ

API ยังไม่ถูกพัฒนา ชื่อและ contract อาจเปลี่ยนหลังทีมตกลง

| Method | เส้นทาง | หน้าที่ |
| --- | --- | --- |
| POST | `/api/session/line` | ตรวจ LINE token และสร้าง session |
| GET | `/api/venues/{venueId}/availability` | ดู snapshot โต๊ะว่างตามคืน |
| GET | `/api/venues/{venueId}/releases` | ดูเวลาเปิดรับ |
| POST | `/api/booking-requests` | ส่งคำขอลูกค้า; ตอบ `202` หลัง broker รับ |
| GET | `/api/me/booking-requests/{requestId}` | ติดตามสถานะคำขอของตน |
| GET | `/api/me/bookings` | ดูรายการจองของตน |
| GET | `/api/staff/venues/{venueId}/customers` | ค้นลูกค้าที่ร้านรู้จัก |
| POST | `/api/staff/venues/{venueId}/booking-requests` | พนักงานส่งคำขอจองแทน |
| GET | `/api/staff/venues/{venueId}/bookings` | ดูรายการจองของร้าน |

API ตั้งค่าร้าน โซน โต๊ะ กฎ และ LINE ดูรายละเอียดฉบับเสนอใน `backend/BACKEND_PLAN.md` ทุก endpoint ต้องตรวจสิทธิ์และขอบเขตร้านฝั่ง server

## 9. แนวทางสถาปัตยกรรมที่เสนอ

LINE OA/LIFF และหน้า staff ติดต่อ Next.js API; API รับคำขอเข้าคิว SQS FIFO; worker ประมวลผลและบันทึกผ่าน transaction ใน PostgreSQL; notification outbox ส่งข้อความแยกจากการตัดสินจอง เทคโนโลยีที่แนะนำ ได้แก่ TypeScript, Supabase PostgreSQL/Auth/Storage และ Node.js worker รายละเอียดเป็นข้อเสนอทางเทคนิค ไม่ใช่สิ่งที่ติดตั้งแล้ว

ฐานข้อมูลควรใช้ transaction, locking และ constraints ป้องกันการจัดสรรซ้อน พร้อม idempotency ที่คงอยู่ในฐานข้อมูล การส่ง API ภายนอกต้องไม่ค้างอยู่ใน transaction การรับคำขอและส่งเข้าคิวมีจุดล้มเหลวแยกกัน จึงต้องมี recovery; worker ยืนยันการรับข้อความหลัง commit และไม่ข้ามงานหัวคิวโดยเงียบ
