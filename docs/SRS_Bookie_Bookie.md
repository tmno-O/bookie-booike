## 1. บทนำ

### 1.1 วัตถุประสงค์

เอกสารนี้กำหนดความต้องการของ Bookie Bookie เพื่อให้ทีมผลิตภัณฑ์ นักพัฒนา ผู้ทดสอบ และผู้เกี่ยวข้องใช้เป็นฐานร่วมกันในการออกแบบ พัฒนา และตรวจรับระบบจองโต๊ะร้านผ่าน LINE OA โดยระบุเรื่องที่ยังต้องตัดสินใจแยกจากขอบเขตที่เสนอ

### 1.2 ปัญหาและเป้าหมาย

ร้านรับจองผ่านแชทหรือโทรศัพท์ พนักงานต้องตอบ ตรวจโต๊ะ และบันทึกด้วยตนเอง อาจตอบช้าและจองซ้อน ระบบเสนอให้ลูกค้าจองผ่าน LINE ของร้าน เห็นสถานะโต๊ะ ส่งคำขอเข้าคิวเดียวกับการจองแทนโดยพนักงาน และให้ร้านจัดการรายการในที่เดียว ผลประหยัดเวลาหรือความเร็วจริงยังต้องวัดในการทดลอง

### 1.3 ขอบเขต

**ขอบเขตที่พัฒนาแล้ว:** เชื่อม LINE และเปิดหน้าจอง, ตั้งค่าร้าน/โซน/โต๊ะ/กฎ, ลูกค้าจองเอง, พนักงานจองแทน, จัดคิวและป้องกันการจองซ้อน, ดูผลและรายการจอง, ยกเลิกและเช็กอิน, ตั้งเวลาเปิดจองและวันปิดร้าน, ส่งแจ้งเตือนเมื่อเปิด LINE push และตั้ง Cron

**ขอบเขตเพิ่มเติมรอตัดสินใจ:** มัดจำ ชำระเงิน คืนเงิน และการเผยแพร่ Rich Menu ผ่านระบบ ดู §8 และ §11

**นอกขอบเขต MVP ที่เสนอ:** POS, ระบบรายงานเชิงวิเคราะห์, ระบบจัดเก็บค่าสมาชิกร้าน, marketplace ค้นหาร้าน และการรับประกันผลทางธุรกิจ การปล่อยโต๊ะอัตโนมัติเมื่อไม่มายังอยู่ในแผน

### 1.4 คำศัพท์

| คำ | ความหมาย |
| --- | --- |
| LINE OA | บัญชี LINE Official Account ของร้าน |
| LIFF | เว็บแอปที่เปิดผ่าน LINE |
| ร้าน (venue) | หน่วยข้อมูลและขอบเขตสิทธิ์ของร้านแต่ละแห่ง |
| คืนบริการ (service night) | ช่วงบริการที่ผูกกับวันที่เริ่มต้น แม้สิ้นสุดหลังเที่ยงคืน |
| Draft | ตัวเลือกที่ยังไม่ส่งคำขอ ไม่มีการกันโต๊ะหรือสิทธิ์ในคิว |
| FIFO | พิจารณาตามลำดับที่ระบบคิวรับคำขอ ภายในร้านและคืนบริการเดียวกัน |
| Hold | การกันโต๊ะชั่วคราวระหว่างรอชำระเงิน หากเปิดใช้มัดจำ |
| Known customer | ลูกค้าที่มีความสัมพันธ์กับร้านและมี identity ที่ระบบระบุได้ |
| Policy snapshot | สำเนานโยบายที่ผูกกับรายการจอง ณ เวลาสร้างรายการ |

## 2. ภาพรวมระบบ

### 2.1 ผู้ใช้งานและสิทธิ์

| ผู้ใช้งาน | หน้าที่ |
| --- | --- |
| ลูกค้า | เปิดหน้าจอง ดูโต๊ะ ส่งคำขอ ติดตามผลและดูรายการของตน |
| เจ้าของร้าน | ตั้งค่าร้าน LINE โซน โต๊ะ กฎ และจัดการรายการตามสิทธิ์ |
| พนักงาน | ค้นลูกค้าที่ร้านรู้จัก จองแทน และดูหรือจัดการรายการตามสิทธิ์ที่ได้รับ |
| ผู้ดูแลระบบ | ดูแลโครงสร้างและแก้ปัญหาระบบ ขอบเขตเครื่องมือดูแลรอยืนยัน |
| ระบบภายนอก | LINE และผู้ให้บริการชำระเงินเมื่อเปิดใช้ |

เจ้าของและพนักงานต้องเป็นสมาชิกของร้านที่เกี่ยวข้อง การเข้าสู่ระบบเพียงอย่างเดียวไม่ให้สิทธิ์เข้าถึงทุกร้าน

### 2.2 สภาพแวดล้อมและข้อพึ่งพา

ลูกค้าใช้ LIFF บนอุปกรณ์มือถือที่รองรับ LINE; เจ้าของและพนักงานใช้เว็บหลังบ้าน ต้องมีอินเทอร์เน็ต ระบบพึ่งพา LINE สำหรับตัวตนและการส่งข้อความ และบริการฐานข้อมูล/คิวตามสถาปัตยกรรมที่เลือกจริง การส่งข้อความจาก OA ต้องตั้งค่า provider และ channel ที่สัมพันธ์กัน การมีลิงก์เพียงอย่างเดียวไม่ยืนยันว่าระบบส่งข้อความได้

### 2.3 สมมติฐานและข้อจำกัด

- หนึ่งโต๊ะมีการจัดสรรที่ active ได้หนึ่งรายการต่อคืนบริการ. การรองรับหลายรอบยังอยู่ในแผน
- สถานะโต๊ะที่แสดงเป็น snapshot อาจเปลี่ยนระหว่างผู้ใช้ตัดสินใจ ผลสุดท้ายตัดสินฝั่ง server
- ลำดับ FCFS เริ่มเมื่อคำขอ commit ลง Postgres. ลูกค้าดูผลจองจาก status API.
- ทีมเปิดระบบบน Vercel และ Supabase และเชื่อม LINE Login/LIFF แล้ว. [หลักฐาน CI และ k6 local](evidence/README.md) ระบุรุ่นและสภาพแวดล้อมที่ทดสอบ.

## 4. กฎธุรกิจและสถานะ

1. สิทธิ์รับโต๊ะเกิดจากการประมวลผลสำเร็จ ไม่เกิดจากการเปิดหน้าหรือบันทึก draft
2. ทั้งลูกค้าและพนักงานใช้ FIFO เดียวกันตามร้านและคืนบริการ ไม่ใช้ลำดับเวลาบนเครื่องลูกค้า
3. ระบบต้องบังคับความถูกต้องที่ฐานข้อมูลเมื่อมีคำขอพร้อมกัน ตามกฎหนึ่งโต๊ะต่อคืน
4. ราคาโต๊ะกับมัดจำเป็นข้อมูลคนละประเภท ราคาไม่กำหนดไม่ได้แปลว่าไม่มีมัดจำเสมอ หากมีการเปิดใช้มัดจำ
5. การส่งข้อความล้มเหลวไม่ย้อนการจองที่บันทึกสำเร็จ
6. วันคืนบริการและเวลาเปิดรับต้องคำนวณจาก timezone ของร้าน

**สถานะคำขอ:** `queued`, `confirmed`, `rejected`. ผล `confirmed` ระดับคำขอหมายถึงสร้าง booking แล้ว.

**สถานะการจองที่ API ใช้:** `pending_allocation`, `confirmed`, `checked_in`, `cancelled`.

## 5. ความต้องการส่วนติดต่อ

### 5.1 ส่วนติดต่อผู้ใช้

- **ลูกค้า:** หน้า LINE Login, ข้อมูลติดต่อ, เลือกคืน/จำนวนคน/โซน, สถานะคำขอ, รายการจองและยกเลิกตามนโยบาย ต้องแสดงข้อความเมื่อโต๊ะไม่ว่างหรือเกิดข้อผิดพลาด
- **เจ้าของ/พนักงาน:** เข้าสู่ระบบ, รายการจอง, ค้นลูกค้าและจองแทน; เจ้าของมีหน้าตั้งค่าร้าน โต๊ะ กฎ และ LINE ตามสิทธิ์
- รองรับจอมือถือใน flow ลูกค้า แสดงสถานะกำลังประมวลผลอย่างชัดเจน ไม่แสดงว่าได้โต๊ะก่อนผลยืนยัน

### 5.2 ส่วนติดต่อระบบภายนอก

- **LINE Login/LIFF:** ตรวจ token และ provider ที่เกี่ยวข้องฝั่ง server
- **LINE Messaging API:** ส่งข้อความจาก OA ร้านเมื่อเปิดใช้งานและตั้งค่าถูกต้อง. Webhook ขาเข้าอยู่ในแผน
- **ระบบคิว:** รับคำขอแบบ FIFO แยกกลุ่มตามร้านและคืนบริการ พร้อมกลไกกู้คืนกรณีส่งหรือประมวลผลล้มเหลว
- **Payment provider:** เฉพาะเมื่ออนุมัติขอบเขต §8; provider และเส้นทางเงินจริงยังไม่เลือก

### 5.3 API หลัก

สัญญาฉบับเต็มอยู่ใน [API contract](API_CONTRACT.md)

| Method | เส้นทาง | หน้าที่ |
| --- | --- | --- |
| POST | `/api/session/line` | ตรวจ LINE token และสร้าง session |
| GET | `/api/venues/{venueId}/availability` | ดู snapshot โต๊ะว่างตามคืน |
| GET | `/api/venues/{venueId}/releases` | ดูเวลาเปิดรับ |
| POST | `/api/booking-requests` | ส่งคำขอลูกค้าและตอบ `202` เมื่อ Postgres รับเข้าคิว |
| GET | `/api/me/booking-requests/{requestId}` | ติดตามสถานะคำขอของตน |
| GET | `/api/me/bookings` | ดูรายการจองของตน |
| POST | `/api/me/bookings/{bookingId}/cancel` | ยกเลิกตามนโยบายร้าน |
| GET | `/api/staff/venues/{venueId}/customers` | ค้นลูกค้าที่ร้านรู้จัก |

| GET | `/api/staff/venues/{venueId}/bookings` | ดูรายการจองของร้าน |

API ตั้งค่าร้าน โซน โต๊ะ กฎ และ LINE ตรวจสิทธิ์และขอบเขตร้านฝั่ง server.

## 8. ข้อเสนอเพิ่มเติมเรื่องมัดจำและคืนเงิน

**สถานะ: รออนุมัติขอบเขตและนโยบาย ไม่ถือว่าเป็น MVP ที่ตกลงแล้ว** แผน backend กล่าวถึงมัดจำสามโหมด แต่เอกสารที่มีไม่ได้ให้คำจำกัดความครบทั้งสามโหมด จึงยังระบุรายละเอียดหรือ refund matrix ไม่ได้

| ID | ความต้องการเมื่ออนุมัติ | เกณฑ์ตรวจรับ |
| --- | --- | --- |
| OPT-01 | ตั้งนโยบายมัดจำและบันทึก snapshot ของยอด เงื่อนไข และ cutoff ในการจอง | การเปลี่ยนนโยบายภายหลังไม่เปลี่ยนสิทธิ์ของรายการเดิม |
| OPT-02 | เมื่อมีมัดจำ กันโต๊ะชั่วคราวและยืนยันเมื่อ provider ยืนยันการชำระ | hold เริ่มเมื่อกันโต๊ะสำเร็จ; หมดเวลาแล้วไม่ยืนยันโต๊ะอัตโนมัติจากเงินที่มาช้า |
| OPT-03 | จัดการ payment event ซ้ำ มาช้า หรือมาไม่ตามลำดับ | ไม่ charge ซ้ำ; เงินหลัง hold หมดถูกบันทึกเป็น `paid_unallocated` และเข้าสู่กระบวนการจัดการที่กำหนด |
| OPT-04 | แสดงสิทธิ์คืนก่อนยกเลิก และคำนวณจาก snapshot เหตุผลและเวลาที่มีผล | ยกเลิก/ปล่อยโต๊ะและสร้างสิทธิ์คืนอย่างสอดคล้องกัน; กฎและจุดตัดเวลาต้องผ่านการอนุมัติ |
| OPT-05 | เมื่อร้านยกเลิกหรือจัดโต๊ะไม่ได้ ให้สิทธิ์คืนเต็มสำหรับรายการที่ชำระแล้ว | ทดสอบครบทุกโหมดที่อนุมัติและตรวจยอดกับ policy snapshot |
| OPT-06 | แยกสิทธิ์คืน การร้องขอคืน ผลคืนเงินจริง และ payout | สถานะ `refunded` เกิดเมื่อมีหลักฐาน provider ยืนยัน ไม่ใช่เพียงส่งคำขอ; retry ไม่คืนซ้ำ |
| OPT-07 | ทดสอบผ่าน sandbox ก่อนเลือกเปิดเงินจริง | ตรวจความสามารถรับเงิน คืนเงิน และ payout ของ provider และอนุมัติ readiness ก่อนใช้งานจริง |

ขณะนี้พนักงานเช็กอินผ่านหน้าแอดมินได้. ระบบคืนโต๊ะอัตโนมัติเมื่อ no-show ยังอยู่ในแผน.

## 9. สถาปัตยกรรมปัจจุบัน

LINE LIFF และหน้า staff ใช้ Next.js API บน Vercel. Postgres เก็บคำขอและจัดสรรโต๊ะใน transaction โดยล็อกตามร้านและคืนและบังคับ unique allocation. API เริ่ม drain หลังตอบ และ Supabase Cron เก็บคำขอค้าง. LINE outbox ทำงานแยกจาก transaction การจอง.
